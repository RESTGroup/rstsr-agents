# api-doc-conventions: rstsr-core docstring policy

Normative conventions for rustdoc docstrings in `rstsr-core` (both item
docstrings in `src/` and the crate-level pages under `src/docs/`). Written for
AI code agents and human contributors alike; designed so a cold session can
apply it without further context. This skill **is** the policy - the canonical,
single source of truth. `rules/api-doc-conventions.md` (rstsr-agents) is a thin
router for agents and humans arriving via the rules path; policy content is
never duplicated there.

Terminology (anchor function, variant, alias, ...) is defined in `CONTEXT.md` at
the root of the `rstsr-agents` repository (where this skill lives). Read that
first; this skill uses those terms throughout.

## 0. Scope and enforcement

This skill applies when: writing or reviewing any docstring in
`rstsr-core/src/` (new API, or an existing docstring - the policy is binding on
touch); adding/changing doc examples, doctests, `# Overloads Table`,
row/column-major notices, or `# Notes of API accordance`; or executing the API
doc campaign (wholesale docstring retrofit).

- **Scope**: `rstsr-core` only. Other crates (device crates, `rstsr-common`,
  ...) may adopt these conventions later; nothing here binds them yet.
- **Normative language**: MUST / MUST NOT / SHOULD / MAY, RFC-2119 style.
  "Function" below also covers methods and macros unless stated.
- **Binding on touch**: any docstring you write or materially modify MUST comply.
  Do **not** opportunistically mass-rewrite untouched docstrings to "fix" style
  drift - wholesale retrofit happens only through the API doc campaign
  (`plans/2026-09-api-doc-campaign.md`, local-only), tracked in
  `rstsr-core/tests/tracking/doc_coverage.csv`.
- **Language**: documentation is always in English, in present tense, third
  person ("Returns a view..." - not "This function will return...").
- **Reference exemplars** (read these before writing docs):
  - `rstsr-core/src/tensor/manipulation/transpose.rs` - anchor docstring, canonical structure.
  - `rstsr-core/src/tensor/manipulation/reshape.rs` - full cannon: ownership-semantics table,
    compile-error tips, elaborated row/col examples.
  - `rstsr-core/src/tensor/asarray.rs` - Overloads Table and hidden-assertion examples.
  - `rstsr-core/src/tensor/linalg/vecdot.rs`, `matrix_transpose.rs` - full style outside manipulation.

## 1. Documentation tiers

Every public item is in exactly one tier:

| Tier | Applies to | Requirement |
|--|--|--|
| **Full** | User-facing anchor functions (see §1.1) | Complete docstring per §3-§8 |
| **Minimal** | Variants, aliases, associated methods, macro-generated operator traits, storage/device/format internals | Summary line + `See also [anchor]` per §2 |
| **Type/module floor** | Types (`TensorBase`, aliases, `Layout`, ...), public modules | §1.2 |

### 1.1 Full-tier module assignment

- `tensor/manipulation/` (done), `tensor/asarray.rs` (done),
  `tensor/linalg/` (`vecdot`, `matrix_transpose` done; `matmul` pending),
  `tensor/creation.rs`, `tensor/creation_from_tensor.rs`, `tensor/indexing.rs`,
  `tensor/adv_indexing.rs`, `tensor/reduction.rs`, `tensor/operators/` (the
  `rt::` free functions), `tensor/map_elementwise.rs`,
  `tensor/ownership_conversion.rs`, `tensor/iterator_axes.rs`,
  `tensor/iterator_elem.rs`, `tensor/assignment.rs`, `tensor/tensor2_impl.rs`.
- When adding a new user-facing function anywhere, it is full tier.

### 1.2 Types and modules

Type-level docstrings are deliberately **free-form** - no template. The floor:

- MUST have an accurate summary paragraph (what the type is, when a user touches it).
- SHOULD cross-link related types (the ownership aliases should reference each
  other and `api_specification`'s structure section).
- Every public module MUST have a `//!` header, at least one line (e.g.
  "Manipulation functions that only change layout.").

### 1.3 What is NOT documented

- `pub use` aliases (e.g. `pub use transpose as permute_dims;`) - rustdoc re-exports
  the anchor's docstring automatically; list the alias in the anchor's variants
  section instead. MAY additionally add `#[doc(alias = "...")]` on the anchor for
  searchability.
- Macro-generated operator traits (`OpAddAPI`, `OpSinAPI`, ... ~200 items from
  `#[duplicate_item]` / `trait_reduction!` / `trait_unary!`). Their modules carry
  a `//!` explaining the generation pattern and pointing to the anchors (§9).

## 2. Anchor and variants

One function family = one anchor + minimized variants.

- **Anchor selection**: the *panic-version free function returning a view*
  (`transpose`, `flip`, `slice`). It gets the full docstring.
- **Exception**: when ownership semantics differ meaningfully inside the family,
  more than one member may be full-tier. Exemplar: the reshape family, where
  `reshape` (borrow -> `TensorCow`) and `into_shape` (owned -> `Tensor`) both
  carry full docs. Use sparingly; default is one anchor.
- **Variant minimized style** (MUST, verbatim shape - same title as anchor, then
  see-also):

  ```rust
  /// Permutes the axes (dimensions) of an array.
  ///
  /// See also [`transpose`].
  ```

  A variant MUST NOT duplicate parameters/examples of the anchor. Longer forms
  already in tree (a `# See also` heading, or a one-line
  `/// # See also [`reshape`], [`into_shape`] ...`) are acceptable; new variants
  use the two-line form.
- **Fallible (`_f`) variants**: add `For a fallible version, use [`<f>`].` to the
  anchor's `# Panics`; the `_f` doc itself stays minimal.
- **Associated methods** on `TensorAny` are variants (minimal), enumerated in the
  anchor's `# See also > Variants of this function` under an
  `Associated methods on `TensorAny`` sub-list.

## 3. Canonical docstring structure (full tier)

Section order (top to bottom). Sections marked *opt* are included only when they
earn their place; the rest are MUST for full-tier anchors unless genuinely
inapplicable.

1. **Title** - one-line summary (this is the rustdoc search/result line). Reuse
   NumPy/array-api wording when a counterpart exists; else write your own.
2. **Prose explanation** - behavior, view-vs-copy, case bullets (1-D/2-D/n-D).
   Ends with the row/col one-liner when behavior is order-independent (§4).
3. **Row/col-major notice** - warning `<div>` when behavior differs by default
   order (§4). *Order-dependent only, but then MUST.*
4. **`# Overloads Table`** (opt) - for overload-heavy functions (§6).
5. **`# Parameters`** - one bullet per parameter, signature style
   `- `tensor`: [`&TensorAny<R, T, B, D>`](TensorAny)` with indented sub-bullets;
   parameter-level overload lists as `- Overloads:` sub-bullets.
6. **`# Returns`** - return type link + ownership notes (view / copy / Cow; when
   data is cloned).
7. **`# Examples`** - per §5. Each fenced example gets a one-line `###`-level or
   prose lead-in ("For a 2-D array, this is the standard matrix transpose:").
8. **`# Elaborated examples`** (opt) - large/complex usage split out of the main
   examples (row/col differences, cloning occasions). `##` subsections inside.
9. **Opt deep-dive sections** (opt) - the three sanctioned ones, in this relative
   order: `# Ownership Semantics between ...` (markdown table; reshape
   exemplar), `# Tips on common compilation errors` (`compile_fail` + `text`
   pair; reshape exemplar), `# Migration Guide` (`ignore` fence;
   into_compatible_shape exemplar).
10. **`# Notes of API accordance`** - §7. MUST when a counterpart exists in
    NumPy / array-api / PyTorch (which is nearly everything - check
    `src/docs/array_api_standard.md`).
11. **`# Panics`** - bullet list of panic conditions, closing with
    `For a fallible version, use [`<func>_f`].` On `_f` functions this section is
    `# Errors` territory but `_f` functions are minimal-tier, so it rarely
    appears. `# Safety` on `unsafe fn` is unaffected by this policy and always
    required.
12. **`# See also`** - three `##` subsections, in order:
    `## Similar function from other crates/libraries` (NumPy / array-api /
    PyTorch / ndarray / SciPy links),
    `## Related functions in RSTSR` (semantic neighbors + aliases),
    `## Variants of this function` (panic/`_f`/`into_*`/`to_*` forms, then the
    `Associated methods on `TensorAny`` sub-list).

**Escape hatch**: if the sanctioned structure does not fit a function, extra
unsanctioned sections MAY be added (placed before `# Notes of API accordance`).
Add them when the function deviates much from common libraries, or when
ownership/layout behavior can confuse newcomers; otherwise only when clearly
necessary.

**Known legacy drift** (do not copy; align only when the docstring is touched,
or in the campaign's sanctioned postfix pass): `# Arguments`/`# Errors` in
`to_contig`/`to_layout` (use `# Parameters`/`# Panics`); `# See Also` capital-A
in `vecdot` (use `# See also`); `Panics` before `Examples` in `flip`/`squeeze`
(canonical position is §3.11); bare `[RowMajor]` links in `reshape`/`broadcast`
(use `[`RowMajor`]`).

## 4. Row/column-major behavior

RSTSR is dual-order: the *same* tensor representation admits row-major
(NumPy-like) and column-major (Fortran/Julia-like) default orders on the device.
Every full-tier function MUST address this explicitly - one of:

**(a) Order-independent** - the one-liner, as the last line of prose before the
first `#` section (MUST be this sentence shape):

```rust
/// This function behaves identically under [`RowMajor`] and [`ColMajor`] device default orders.
```

**(b) Order-dependent** - the warning div (verbatim template):

```rust
/// <div class="warning">
///
/// **Row/Column Major Notice**
///
/// This function behaves differently on default orders ([`RowMajor`] and [`ColMajor`]) of device.
///
/// </div>
```

plus: at least one example per affected mode in `# Examples` or
`# Elaborated examples` (typically a `## Difference between [RowMajor] and
[ColMajor]` subsection), and a link to the standalone order-semantics page:
`[`order_semantics`](crate::order_semantics)` (source:
`rstsr-core/src/docs/order_semantics.md`, wired as a `pub mod` like
`api_specification`).

Rules:

- Computation functions and layout-only manipulations are usually (a) - but say
  so explicitly; never leave the topic silent.
- Known (b) families: `reshape`/`into_shape`/`change_shape`/`reshape_with_args`,
  `asarray` (shape input), `broadcast` and every broadcasting function, creation
  functions with shape input (`zeros`, `ones`, `full`, `eye`, `arange`+shape, ...),
  `to_layout`/`to_contig`/`to_prefer`, `into_compatible_shape`.
- The **broadcast-rule asymmetry** (row-major aligns shapes from the *last*
  axis, NumPy-style; column-major from the *first* axis, Fortran/Julia-style) is
  documented **once** on the order-semantics page (which also covers what the
  default order controls and reshape's iteration invariance) and linked from
  every broadcasting function's notice. Do not restate the rule in every
  docstring.
- `tensor_from_nested!` always produces row-major layout regardless of device
  order - keep documenting that locally (it is a (b) fact about the macro, not
  about the order system).

## 5. Examples and doctests

Examples are **real rustdoc doctests**: they MUST compile and pass under default
features (`row_major` + CPU) via `cargo test -p rstsr-core --doc`, which runs in
CI. The facade crate is a dev-dependency precisely so `use rstsr::prelude::*;`
resolves inside doctests.

**Canonical skeleton** (hidden setup MUST be hidden; no visible-setup exception,
even for the first example):

```rust
/// ```rust
/// # use rstsr::prelude::*;
/// # let mut device = DeviceCpu::default();
/// # device.set_default_order(RowMajor);
/// let a = rt::tensor_from_nested!([[1, 2], [3, 4]], &device);
/// let result = a.transpose(None);
/// println!("{result}");
/// // [[ 1 3]
/// //  [ 2 4]]
/// # let expected = rt::tensor_from_nested!([[1, 3], [2, 4]], &device);
/// # assert!(rt::allclose(&result, &expected, None));
/// ```
```

- **Output MUST be real**: paste from an actual run; never invent or predict.
  Shown output lines stay byte-identical to the run (§5.1 procedure).
- **Output display**: tensors via Display (`println!("{result}")`) when values
  are the point; via Debug (`println!("{a:?}")`) when layout is the point - the
  Debug form appends the `N-Dim (dyn), contiguous: ..., shape: ..., stride:
  ..., offset: ...` line. Multi-line output: first line on the `// ` comment of
  the `println!` line; continuation lines each on their own `// ` line,
  preserving the printed layout.
- **Hidden verification lines** (`# let expected = ...; # assert!(...)`)
  SHOULD follow value-printing examples. Mind the `allclose` broadcast gotcha
  (`tests/CONTEXT.md`): prefer shape-checked assertions.
- **Determinism**: examples MUST be deterministic. Prefer integer dtypes to
  avoid float-format noise; avoid random data (use `rt::arange` /
  `tensor_from_nested!`).
- **Example splitting**: `# Examples` holds the small/common usages; anything
  large or complex moves to `# Elaborated examples` with `##` subsections.

**Special fences** (sanctioned, sparingly):

- ` ```rust,should_panic ` - only when the panic itself is the documented behavior.
- ` ```compile_fail ` + ` ```text ` pair - for common ownership/compile errors:
  the failing snippet, then the pasted compiler error, then the working
  alternative (reshape exemplar).
- ` ```ignore ` - migration guides only.

### 5.1 The doc_draft procedure (mandatory agent workflow)

Every docstring example MUST originate from a runnable `doc_draft` test
(`rstsr-core/tests/doc_draft/<category>/test_<func>.rs`, `mod doc_<func>`;
see skills `core-test` + `test-conventions`). Direction of truth:
**doc_draft first, docstring second** - never the reverse.

1. Write/extend the `doc_<func>` test with the example; `println!` the results.
2. Run it and capture real output:
   `cargo test -p rstsr-core --test entry_row_cpu --features "backtrace row_major" --no-default-features -- doc_<func> -- --nocapture`
3. Paste the actual output into `// ` comments in the test - never invent it.
4. Assert in the test: values (`assert_equal` / `rt::allclose`) **and**, for any
   output that will be displayed in the docstring, output-string equality
   (`assert_eq!(format!("{result}"), "[[ 1 3]\n [ 2 4]]")`). The string
   assertion is the MUST that keeps pasted output honest.
5. Copy the example into the docstring: add hidden `#` setup lines, keep the
   shown output byte-identical to the run.
6. Verify: `cargo test -p rstsr-core --doc` (CI runs this too).

Byte-identity between docstring and `doc_draft` is NOT required (the docstring
may trim/hide lines), but displayed output lines MUST come from the run
unchanged, and any drift MUST be applied doc_draft-first.

## 6. Overloads

RSTSR overloads via tuple arguments (`rt::asarray((vec, shape, &device))`).

- Overload-heavy functions (`asarray`, `sum_axes`, creation functions, ...)
  MUST carry a `# Overloads Table` on the anchor, in the `asarray` style:
  `##` groups by output type, then full-signature bullets:
  `- `asarray((input: Vec<T>, shape: D, device: &B)) -> Tensor<T, B, IxD>``.
  Complete list of tuple forms; grouping prose for families ("Also, overloads
  for `&Vec<T>` that behave the same as `&[T]`").
- Mild overloading (a parameter accepting several types) uses parameter-level
  `- Overloads:` sub-bullets in `# Parameters` instead (reshape's `shape`
  exemplar) - no table.
- Examples cover the typical 2-4 forms, not every overload.
- Hand-written API traits backing an overloaded function (e.g. `AsArrayAPI`)
  SHOULD link to the anchor's table (or repeat it); macro-generated operator
  traits are exempt (§1.3).

## 7. API accordance and external references

`# Notes of API accordance` (MUST when a counterpart exists):

- The signature triple, each with an inline link:

  ```rust
  /// # Notes of API accordance
  ///
  /// - Array-API: `permute_dims(x, /, axes)` ([`permute_dims`](https://data-apis.org/array-api/2024.12/API_specification/generated/array_api.permute_dims.html))
  /// - NumPy: `transpose(a, axes=None)` ([`numpy.transpose`](https://numpy.org/doc/stable/reference/generated/numpy.transpose.html))
  /// - RSTSR: `tensor.transpose(axes)` or `rt::transpose(&tensor, axes)`
  ```

  Plus prose for signature/semantic differences ("Please note this function does
  not support `order` and `copy` arguments in NumPy's `reshape`.").
- **Citation policy**: cite when rstsr's semantics are intentionally modeled on
  the source. Defaults: NumPy and the Python Array API standard (use the pinned
  `2024.12` spec links, matching `src/docs/array_api_standard.md`'s conformance
  target). PyTorch (`torch.index_select`), rust `ndarray` (`to_shape`,
  `into_dimensionality`), SciPy: cite when actually modeled on them. External
  links are inline-style with backticked labels.
- NumPy **behavior differences** for row-major usage are documented inline here
  (self-contained for docs.rs) per the three-layer scheme in §8.

## 8. NumPy differences: three layers

1. **Registry (source of truth)**:
   `rstsr-core/tests/tracking/numpy_differences.md`, one `##` heading per rstsr
   function (stable anchors), entries tagged `intentional` / `bug` /
   `col-major-transfer`. This is the layer AI agents read when porting NumPy
   code to rstsr. A divergence is either a bug (fix it) or an intentional
   difference (record it) - never only a code comment (skill `test-conventions`
   §6).
2. **Docstring (self-contained)**: the difference is stated fully inline in
   `# Notes of API accordance`. No dead-end links: a docs.rs reader gets the
   complete statement.
3. **Published report (humans)**: a rstsr-book page mirroring the registry -
   manual mirror first, scripted generation later only if drift hurts.
   Docstrings link the book URL once it exists; until then, the GitHub blob URL
   of the registry.

## 9. Operators and macro-generated surfaces

- Anchors are the `rt::` free functions and `TensorAny` methods (e.g. `rt::sin`,
  `rt::add`, `%`-as-matmul), documented full-tier like any other anchor -
  including `# Notes of API accordance` (array-api elementwise/binary specs) and
  the `%` remainder-vs-matmul surprise called out explicitly.
- The trait files (`src/operators/ops/*`, `src/tensor/operators/*`) get **module
  `//!` docs** explaining the generation pattern (`#[duplicate_item]`,
  `trait_unary!`, ...) and pointing to the anchors - not per-trait docstrings.
- `src/docs/api_specification.md` and `src/docs/array_api_standard.md` remain
  the API-index / conformance views. Keep them in sync only when the *API
  surface* changes (not when docstrings change).

## 10. Micro-style rules

- Intra-doc links are always backticked: `[`transpose`]`, `[`RowMajor`]` -
  never bare `[transpose]`. Function-call links `[`change_shape`](change_shape())`
  and juxtaposed inline code `` [`reshape_with_args`]`(shape, order) `` are
  sanctioned forms.
- Headings are sentence-case: `# See also` (not `# See Also`), `# Parameters`,
  `# Returns`, `# Examples`, `# Panics`, `# Overloads Table`,
  `# Elaborated examples`, `# Notes of API accordance`.
- `# Safety` on `unsafe fn` follows rustdoc norms and is always required,
  independent of tiers.
- Warning divs use exactly the `<div class="warning">` shape in §4 (blank
  `///` lines around the bold header). Other div headers (e.g.
  `**Deprecated**`, `**Different Signature Convention to ...**`) follow the same
  shape.
- Math: KaTeX is wired (`katex-header.html`, `$$...$$` display math) - MAY be
  used sparingly (e.g. reduction formulas).

## 11. Enforcement and tracking

- **CI**: `cargo test -p rstsr-core --doc` runs in `rstsr-core-test.yml`
  (doctests job). All docstring examples MUST pass it. Baseline at adoption:
  90 passed / 0 failed / 2 ignored.
- **Tracking**: `rstsr-core/tests/tracking/doc_coverage.csv` - module-level
  rows (`module,category,tier,status,batch,notes`); update the row when a
  module's status changes. Per-item granularity may be added inside a batch.
  Statuses: `done` (policy-compliant), `postfix` (documented before the policy;
  compliance pass pending - see the campaign plan's postfix pass), `partial`,
  `todo`, `na`.
- **`#![warn(missing_docs)]`**: deferred until most items are documented (end of
  the campaign); do not enable earlier - it would flood.
- **AI-attribution exception**: per the project-wide CLAUDE.md notice, large
  AI-generated files carry a generation note - **API docstrings are exempt**:
  they are assumed AI-writable and not all manually reviewed. Attribution for
  doc work lives in commit messages/PRs (skill `git-commit-coauthor`), never in
  the docstrings or published docs.
- **Review posture**: docstrings are "partial AI usage" territory (CLAUDE.md) -
  expect human review of semantic claims (ownership, panics, NumPy-difference
  statements), not of formatting.
