# Prelude conventions (rstsr workspace)

This skill is the reference for the **user-facing prelude** (`prelude`, and the `rt::` surface it
exposes): how an item travels from its defining module into it, and how a member crate is wired
into the `rstsr` facade's prelude. It describes the tree as of 2026-10-03 (branch
`261003/rstsr-cpu-dlpack`); §5 lists the deviations that exist today — do not "fix" one blindly.

- User-facing documentation (import side): `rstsr-book/docs/fundamentals/00-installation.mdx`,
  "Prelude Import Guide" — four groups, `rt`, naming-conflict guidance.
- Docstring policy for the items you export: skill `api-doc-conventions`.
- Paths below are relative to the rstsr workspace root (the facade crate lives in `rstsr/`).

## 1. Where the user-facing prelude lives

- Library crates with user-facing API carry `src/prelude.rs` (`pub mod prelude` in `lib.rs`):
  `rstsr-core`, `rstsr-common`, `rstsr-linalg-traits`, `rstsr-sci-traits`, `rstsr-blas-traits`,
  `crates-plugin/rstsr-tblis`, and the facade `rstsr` (whose public surface is essentially its
  prelude — it contains no code).
- `crates-device/*` have no prelude of their own; their device types reach users through the
  facade's `rstsr_structs` (§4).
- `rstsr-dtype-traits` and `rstsr-test-manifest` have no prelude at all (see §5).

## 2. The user-facing prelude: four namespaces

Grouped into up to four modules, plus optional extras:

- `rstsr_funcs` — free functions (`arange`, `sum`, `sin`, ...), the `rt::` surface;
- `rstsr_traits` — the `*API` traits backing operations;
- `rstsr_structs` — types, aliases, enums (`Tensor`, `Layout`, `DeviceCpuSerial`, ...);
- `rstsr_macros` — macros (`slice!`, `tensor_from_nested!`, ...);
- `rstsr_mods` — extra, only `rstsr-sci-traits` (nested module namespaces).

**Top-level glob rule** (core, common, facade): at the bottom of `prelude.rs`, `rstsr_macros`,
`rstsr_structs` and `rstsr_traits` are globbed into the prelude root, but **`rstsr_funcs` is not** —
so `use rstsr::prelude::*` brings types/traits/macros but not hundreds of function names.

**`pub mod rt`** (core, common, facade only): re-exports the namespaces *and* their contents, so
users write:

```rust
use rstsr::prelude::*;
let b: Tensor<f64, _> = rt::sin(&a);     // functions come from rt::
```

`rt` also carries `Error`/`Result` (core/common), `rt::blas` (blas-traits alias, §4) and the
per-feature submodule names (`rt::linalg`, `rt::tblis`, `rt::dlpack`, ...).

## 3. The flow of one item (rstsr-core example)

1. **Define** it in its module, e.g. a function in `rstsr-core/src/tensor/manipulation/reshape.rs`,
   with its docstring on the panic version and the `_f` twin beside it.
2. **Publish it from the module** through the module's inline `exports` block (see §3.1).
3. **List it in the user prelude** `rstsr-core/src/prelude.rs`, in the matching namespace, both
   variants:

   ```rust
   pub mod rstsr_funcs {
       pub use crate::tensor::manipulation::exports::{
           change_shape, change_shape_f, reshape, reshape_f, /* ... */
       };
   }
   ```

   Traits go to `rstsr_traits`, types to `rstsr_structs`. Items may also be listed by direct module
   path (`crate::tensor::adv_indexing::{take, take_f}`) — both styles exist.
4. **(Facade members only) forward it** in `rstsr/src/prelude.rs` (§4); for `rstsr-core` this is
   already the case (`pub use rstsr_core::prelude::rstsr_funcs::*;`).

### 3.1 The `exports` blocks

Each major internal module republishes its public surface through an inline block (there is no
`exports.rs` file anywhere):

```rust
// rstsr-core/src/tensor/manipulation/mod.rs
pub mod exports {
    use super::*;

    pub use broadcast::*;
    pub use reshape::*;
    /* ... one glob per sibling submodule ... */
}
```

The seven blocks: `rstsr-core/src/tensor/mod.rs` (also re-globs the nested
`linalg`/`manipulation`/`operators` exports), `tensor/manipulation/mod.rs`, `tensor/linalg/mod.rs`,
`tensor/operators/mod.rs`, `operators/mod.rs`, `storage/mod.rs`, and
`rstsr-common/src/layout/mod.rs`.

- They are the canonical path used in doc links, e.g.
  `[broadcast_arrays](crate::tensor::manipulation::exports::broadcast_arrays())`.
- They carry no doc comments today; feature gating is done by cfg-gating the underlying module
  declarations, not inside `exports`.
- Not every module has one (§5.5) — check before assuming.

## 4. The facade `rstsr` and optional member crates

The facade contains no code — its public surface *is* `rstsr/src/prelude.rs`. It forwards
`rstsr-core`/`rstsr-common` verbatim and adds optional crates behind Cargo features:

- **device crates** (`crates-device/*`): their *types* are re-exported individually inside
  `rstsr_structs` (`#[cfg(feature = "openblas")] pub use rstsr_openblas::DeviceOpenBLAS;`), plus the
  mutually exclusive `DeviceBLAS` alias blocks. They have no user prelude of their own.
- **blas-traits**: the whole flat prelude is aliased inside `rt`:
  `pub use rstsr_blas_traits::prelude as blas;` (`rt::blas::...`).
- **member crates with functions** (`rstsr-linalg-traits`, `rstsr-sci-traits`, `rstsr-tblis`,
  `rstsr-cpu-dlpack`): the namespaced pattern below.

### 4.1 The namespaced member-crate pattern (canonical)

1. The member crate ships `prelude` with its own `rstsr_traits` / `rstsr_structs` / `rstsr_funcs`
   groups (only the groups it has items for), e.g. `crates-interop/rstsr-cpu-dlpack/src/prelude.rs`.
2. The facade manifest gets an optional dependency and a feature:

   ```toml
   rstsr-cpu-dlpack = { workspace = true, optional = true }   # workspace entry has default-features = false
   dlpack = ["dep:rstsr-cpu-dlpack", "rstsr-cpu-dlpack?/half"]  # forward only crate-local features
   ```

   Also add the feature to `[package.metadata.docs.rs] features`.
3. The facade prelude gets, inside each namespace the member has items for *and* once at prelude
   level:

   ```rust
   // rstsr/src/prelude.rs
   pub mod rstsr_funcs {
       #[cfg(feature = "dlpack")]
       pub mod dlpack {
           pub use rstsr_cpu_dlpack::prelude::rstsr_funcs::*;
       }
   }

   #[cfg(feature = "dlpack")]
   pub mod dlpack {                                  // convenience group for direct access
       pub use rstsr_cpu_dlpack::prelude::rstsr_funcs::*;
       pub use rstsr_cpu_dlpack::prelude::rstsr_structs::*;
       pub use rstsr_cpu_dlpack::prelude::rstsr_traits::*;
   }

   pub mod rt {
       #[cfg(feature = "dlpack")]
       pub use super::dlpack;                        // makes `rt::dlpack::func(...)` work
   }
   ```

4. User-visible result: **`rt::dlpack::into_dlpack(...)`** with cargo feature `rstsr/dlpack`.
   The CHANGELOG announces such wiring the same way ("available from `rt::tblis::einsum` (with
   cargo feature `rstsr/tblis` enabled ...)", TBLIS plugin entry, v0.6.0-alpha.1).
5. Feature hygiene: never forward the member's `row_major`/`col_major`/`std` (they only forward to
   `rstsr-core`/`rstsr-common`, which the facade already controls; forwarding the member's default
   `row_major` would collide with a `col_major` facade build). Forward only member-local features
   (e.g. `half`).
6. Test the wiring with a feature-gated test that calls through the namespace, e.g.
   `test_dlpack_prelude` in `rstsr/src/lib.rs` (`rt::arange_f` → `rt::dlpack::into_shared_dlpack_f`
   → `rt::dlpack::to_dlpack_shared`), then:
   `cargo test -p rstsr --features "backtrace row_major dlpack" --no-default-features`.

## 5. Deviations in the current tree (verified 2026-10-03; do not copy accidentally, do not "fix" without the maintainer)

1. `rstsr-blas-traits` has a **flat** prelude (no `rstsr_*` groups); the facade exposes it as
   `rt::blas` by aliasing the whole module.
2. `rstsr-dtype-traits` has **no prelude at all** (crate-root globs); consumers import the items
   they need by explicit list.
3. `rstsr-common` has no `rstsr_funcs` group (it exposes no free `rt`-level functions).
4. `rstsr-sci-traits` is the only crate with a `rstsr_mods` group, per-submodule preludes
   (`distance/prelude.rs`, `integrate/prelude.rs`) and top-level `distance`/`integrate` modules.
5. `exports` coverage is partial: modules without one use direct globs (`device_cpu_serial/mod.rs`,
   `feature_rayon/mod.rs`, `operators/ops/mod.rs`, `tensorbase` via `lib.rs`; `device_faer` and
   `format` have none). `rstsr-common` has exactly one (layout). `rstsr-common/src/layout/mod.rs`
   also *defines* traits inside its `exports` module (unique); `#[allow(unused_imports)]` sits on
   only two of the seven blocks.
6. Only core/common/facade define `pub mod rt`; member crates stop at the grouped namespaces.
7. The book's configuration note still says "The OpenBLAS backend is not yet integrated into the
   `rstsr` library's prelude" — stale; it is (`#[cfg(feature = "openblas")]` in
   `rstsr/src/prelude.rs`).

## 6. Checklist — add a new function to the prelude

- [ ] Defined with the workspace naming (`_f` fallible twin; docstring on the panic version, see
      skill `api-doc-conventions`).
- [ ] Exported from its module's `exports` block, if that module has one (else by direct path).
- [ ] Listed in the crate `prelude` (`rstsr_funcs` — and its `*API` trait in `rstsr_traits`,
      argument/result types in `rstsr_structs`).
- [ ] If the crate is a facade member: forwarded in `rstsr/src/prelude.rs` under the right
      `#[cfg(feature = ...)]` (§4.1).
- [ ] Verified: `cargo test -p rstsr --features "backtrace row_major <feature>" --no-default-features`
      (plus `cargo clippy ... -D warnings`, `cargo +nightly fmt`, `cargo doc --no-deps`).
